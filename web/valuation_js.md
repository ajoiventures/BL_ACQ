# Valuation browser behavior

`valuation.js` edits request packets and renders responses. It never computes a DCF, event-weighted value, entry ceiling, scenario weight below price, or reverse valuation in the browser. The display defines scenario weights as user assumptions; the compatibility keys `downside_probability` and `max_downside_probability` do not represent a calibrated probability of realized loss. Local arithmetic is limited to percentage display/serialization and chart geometry. Numeric assumptions remain actual USD; field percentages are converted to decimal fractions before sending the packet.

The page reads public examples from `GET /api/valuation/examples`, reuses an existing same-origin HTTP-only session, and signs in through `POST /api/session`. Calculations use `POST /api/valuation/evaluate`. A revision counter rejects a calculation response if an input changed while the request was in flight. Any input edit marks the displayed report stale and disables its save and export buttons.

Saving posts `{request_id, packet}` to `/api/valuation/runs`. After an uncertain transport or server failure the page retains the same body and operation ID for Retry save, so the service can return the existing receipt instead of creating a duplicate. Confirmed saves can be reopened through the history routes with their original inputs. Export contains the evaluated request and the returned report together, plus the digest and optional saved run ID.

All source text, labels, reasons, and notes are inserted through `textContent` or text nodes. Source links permit only credential-free HTTP(S) URLs. Access keys are not saved in browser storage. Source-review controls record user assertions; the report explicitly states that linked source content has not been independently verified by the browser.

Annual path arrays are preserved exactly. The annual-path toggle explicitly removes or restores them; the UI identifies overridden scalar assumptions. Advanced packet edits must be applied before calculation. A structural guard checks nested objects, source/scenario record arrays, and string-reference arrays before replacing the current packet. Invalid pasted structure leaves the previous packet and displayed report intact; the unapplied JSON remains marked stale. Partial policy objects inherit the service's documented defaults so every effective policy input is visible in the form. The server remains responsible for financial validation, including numeric ranges, probability totals, stale sources, claim double counting, currency, and qualification evidence.
